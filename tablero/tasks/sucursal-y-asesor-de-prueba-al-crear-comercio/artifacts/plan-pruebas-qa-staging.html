Plan de pruebas · qa y staging con Merchants Dev

Tarea 98 · escrito el 2026-10-02 · es un plan, todavía no se ejecutó nada en qa ni en staging · solo vale para ambientes de prueba (producción tiene su propio plan)

La idea en una línea. Que el wizard de qa (y después el de staging) inicie sesión con Merchants Dev, para que los asesores de prueba que crea el admin puedan entrar. Si algo sale mal, se vuelve a la configuración de hoy en pocos minutos.

Qué se sabe y qué no

Verificado el 2026-10-02 Cada wizard (dev, qa, staging) es un servicio propio con su secret. Los tres apuntan hoy al mismo login y al mismo cliente (auth.merchant.creditop.com, cliente il7p9ueb…). El servicio lee del secret solo el dominio, el cliente y el secreto del cliente (más la URL de retorno). Cada arranque toma la versión «actual» del secret.
Verificado en dev localCon un cliente nuevo en Merchants Dev y esos tres valores en el .env, el asesor de prueba entra al wizard (a mano y con harness-login-check).
Sin verificar(1) Si el wizard desplegado de qa necesita algo más que esos tres valores. (2) Si el gateway que valida tokens antes del backend acepta el pool nuevo: los autorizadores de dev apuntan a otros pools. (3) Cuánto tarda de verdad el redespliegue de qa. Se resuelven en el ensayo del paso 0.

Qué se puede deshacer y qué no

Se deshace fácil: la configuración del wizard. Vive en un secret con versiones: se guarda la actual, se pone la nueva y, si hace falta, se devuelve la anterior y se reinicia el servicio.

No se toca nunca: el cognito_id de las cuentas que ya existen. La base de datos es la misma para dev, qa y staging, y el backend reconoce a cada asesor por ese valor. No hace falta tocarlo: las cuentas nuevas nacen en Merchants Dev y las viejas siguen en su pool.

El costo real. Mientras qa apunte a Merchants Dev, el equipo de QA no puede entrar con sus cuentas actuales (viven en el pool viejo). Se hace en una hora tranquila, avisando antes, y con una regla de salida clara.

Pasos

  1. Antes · sin riesgo Paso 0 · ensayar la vuelta. En un secret que no importe (el del wizard de dev) cambiar un valor irrelevante, redesplegar, devolver la versión anterior y comprobar que el servicio arranca igual. Así se sabe cuánto tarda y que el comando de vuelta funciona antes de necesitarlo.
  2. Miguel · solo agrega Paso 1 · crear el cliente de qa en Merchants Dev. No afecta a nadie y se puede borrar. Un cliente por ambiente, para que cada uno tenga su secreto y quitar uno no toque al otro. 
    export AWS_PROFILE=dev AWS_DEFAULT_REGION=us-east-2
aws cognito-idp create-user-pool-client --user-pool-id us-east-2_Mh2hIqeQ5 --client-name wizard-qa --generate-secret --allowed-o-auth-flows code --allowed-o-auth-flows-user-pool-client --allowed-o-auth-scopes openid phone email --callback-urls https://originaciones-qa.dev.creditop.com/auth/callback --logout-urls https://originaciones-qa.dev.creditop.com https://originaciones-qa.dev.creditop.com/ --supported-identity-providers COGNITO --explicit-auth-flows ALLOW_REFRESH_TOKEN_AUTH --prevent-user-existence-errors ENABLED > /tmp/wizard-qa-client.json
  3. Miguel · el día del cambio Paso 2 · avisar y confirmar la hoja de vuelta. Avisar al equipo de QA de la ventana y volver a leer la versión actual del secret (tiene que coincidir con la tabla de arriba). 
    aws secretsmanager describe-secret --secret-id dev/loan-request-wizard-qa --query VersionIdsToStages
  4. Miguel · el cambio Paso 3 · poner el login nuevo en el secret. Cambia solo tres claves; el resto queda igual. Imprime únicamente el id de la versión nueva: anótalo, es lo que se necesita para volver. 
    SECRET=dev/loan-request-wizard-qa
NEW=$(aws secretsmanager get-secret-value --secret-id $SECRET --query SecretString --output text | jq -c --slurpfile c /tmp/wizard-qa-client.json '.COGNITO_DOMAIN="merchant-develop.auth.us-east-2.amazoncognito.com" | .COGNITO_CLIENT_ID=$c[0].UserPoolClient.ClientId | .COGNITO_CLIENT_SECRET=$c[0].UserPoolClient.ClientSecret')
aws secretsmanager put-secret-value --secret-id $SECRET --secret-string "$NEW" --query VersionId --output text
  5. Miguel · el cambio Paso 4 · reiniciar el servicio y esperar. 
    aws ecs update-service --cluster inertia-develop --service loan-request-wizard-qa --force-new-deployment --query 'service.deployments[0].rolloutState' --output text
aws ecs wait services-stable --cluster inertia-develop --services loan-request-wizard-qa
  6. Miguel · la prueba Paso 5 · comprobar que el asesor de prueba entra. Crear un comercio en el admin de dev (la base es la misma que usa qa) y correr, desde la raíz de playground: 
    make harness-login-check TARGETS=qa ALLIED=last BLOQUE=98
    Sin la clave en la shell solo descubre a qué login manda qa: debe decir merchant-develop….
  7. Decisión Paso 6 · seguir o volver. Ver la regla de salida abajo.

Regla de salida

Se queda si el asesor de prueba entra al wizard de qa y llega a la sucursal que le corresponde.

Se vuelve si no entra, si el wizard no levanta, o si pasan 30 minutos sin resolverlo. No se investiga con qa bloqueado: se vuelve y se investiga después.

Cómo se vuelve

aws secretsmanager update-secret-version-stage --secret-id dev/loan-request-wizard-qa --version-stage AWSCURRENT --move-to-version-id c6a02706-73fb-48a4-8f5f-d1bf55e1c6e2 --remove-from-version-id NUEVA_VERSION_ID
aws ecs update-service --cluster inertia-develop --service loan-request-wizard-qa --force-new-deployment --query 'service.deployments[0].rolloutState' --output text
aws ecs wait services-stable --cluster inertia-develop --services loan-request-wizard-qa

Comprobar la vuelta: make harness-login-check TARGETS=qa debe volver a decir auth.merchant.creditop.com, y alguien del equipo de QA entra con su cuenta de siempre. Lo creado por la prueba (el cliente wizard-qa, el comercio de prueba y sus cuentas) no molesta y se limpia aparte.

Staging

Se repite igual, solo después de que qa quede bien y se haya vivido un tiempo: otro cliente (wizard-stg) con la URL de retorno de staging, el secret dev/loan-request-wizard-stg, el servicio loan-request-wizard-stg y la versión de vuelta def326e3-…. El admin de staging no hace falta tocarlo: el comercio de prueba se crea en el admin de dev y la base es compartida.

Lo que este plan no resuelve

  • Las cuentas del equipo de QA no pasan a Merchants Dev. Si algún día se quiere que QA entre por ahí, hay que crearlas allí y cambiarles el cognito_id, y eso sí es una decisión aparte porque la base es compartida y no se deshace con un comando.
  • Mientras qa use Merchants Dev, staging y dev desplegado siguen con el login viejo: los ambientes quedan, por un tiempo, con logins distintos.
